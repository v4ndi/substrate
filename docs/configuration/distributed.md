# Распределённый запуск, AMP и DDP

Четыре блока конфига описывают, **как** выполнять прогон — в отличие от
остальных, которые описывают, **что** выполнять:

```yaml
distributed:
  backend: null                    # null -> nccl на GPU, gloo иначе
  timeout_sec: 36000000
  gradient_accumulation_steps: 1
amp: no                            # no | fp16 | bf16
ddp:
  find_unused_parameters: False
  gradient_as_bucket_view: True
  broadcast_buffers: True
  static_graph: False
compile: null                      # null | inductor | ...
```

Все четыре необязательны: без них получится однопроцессный запуск в fp32 без
компиляции.

## Запуск

```bash
# один процесс, без лаунчера
python -m avatar.train --config-dir=configs --config-name=my_run

# все GPU одной машины
torchrun --standalone --nproc_per_node=8 -m avatar.train \
    --config-dir=configs --config-name=my_run
```

Код не различает эти два случая: без `torchrun` в окружении нет `WORLD_SIZE`,
поэтому размер мира равен 1, группа процессов не создаётся, а модель не
оборачивается в DDP. Один и тот же конфиг работает и там, и там.

Инференс запускается так же — `python -m avatar.inference` или под `torchrun`.

### Несколько узлов

Та же команда на каждом узле, плюс параметры рандеву:

```bash
torchrun \
    --nnodes=2 --node_rank=0 --nproc_per_node=8 \
    --rdzv_backend=c10d --rdzv_endpoint=head-node:29500 \
    -m avatar.train --config-dir=configs --config-name=my_run
```

На втором узле — то же самое с `--node_rank=1`. `RANK`, `LOCAL_RANK` и
`WORLD_SIZE` расставляет `torchrun`; код читает их и ничего не выставляет сам.

Настройки NCCL намеренно не задаются в коде: запись в `os.environ` на импорте
невидима в месте вызова, а одна из прежних таких настроек
(`CUDA_LAUNCH_BLOCKING=1`) сериализовала все обращения к CUDA. Если вам нужен
специфический тюнинг NCCL — задавайте переменные в скрипте запуска.

## `distributed:`

| ключ | по умолчанию | что делает |
|---|---|---|
| `backend` | `null` | бэкенд группы процессов; `null` → `nccl` при наличии CUDA, иначе `gloo` |
| `timeout_sec` | `36000000` | таймаут коллективных операций |
| `gradient_accumulation_steps` | `1` | сколько микробатчей приходится на один шаг оптимизатора |

Бэкенд стоит задавать явно только в одном случае: когда нужно поднять несколько
рангов на одной машине с одной видеокартой (например, в тестах). Два ранга NCCL
не могут делить одно устройство, два ранга gloo — могут.

### Накопление градиента

При `gradient_accumulation_steps: N` цикл делает `N` проходов вперёд-назад и
только потом шаг оптимизатора. Между накоплениями всеранговая синхронизация
градиентов пропускается (`no_sync`) — ради этого накопление и нужно.

Из этого следуют две вещи, о которых легко забыть:

* **Эффективный размер батча** равен `batch_size * world_size * N`. Увеличив
  `N`, вы увеличили батч, а не сэкономили память при том же батче.
* **Планировщик шагает раз на границу накопления**, а не на каждый батч.
  Поэтому бюджет шагов — это `эпохи * батчи / N`. Если вы задаёте
  `scheduler.num_training_steps` вручную, считайте его именно так.

## `amp:` — смешанная точность

Одно скалярное значение, не блок:

| значение | что происходит |
|---|---|
| `no` | всё в fp32 (по умолчанию) |
| `fp16` | `autocast` в float16 + `GradScaler` |
| `bf16` | `autocast` в bfloat16, без масштабирования потерь |

Масштабирование потерь включается только для `fp16` и только на CUDA: bf16 имеет
диапазон fp32 и в нём не нуждается. На Ampere и новее `bf16` обычно
предпочтительнее — та же экономия памяти без риска переполнения.

Если задан `clip_grad_norm`, обрезка выполняется **после** снятия
масштабирования: обрезать масштабированный градиент значило бы обрезать по
неверной норме.

## `ddp:`

Передаётся в `torch.nn.parallel.DistributedDataParallel` как есть.

| ключ | по умолчанию | когда менять |
|---|---|---|
| `find_unused_parameters` | `False` | `True`, если в графе есть параметры, не получающие градиент на каждом шаге (например, ветка, включаемая по условию). Стоит заметных накладных расходов — включайте только при ошибке DDP о неиспользованных параметрах |
| `gradient_as_bucket_view` | `True` | экономит память; выключать почти никогда не нужно |
| `broadcast_buffers` | `True` | `False`, если буферы (например, статистики BatchNorm) должны жить на ранге независимо |
| `static_graph` | `False` | `True` даёт оптимизацию, если граф не меняется между итерациями; несовместимо с частью сценариев checkpointing |

## `compile:`

`null` — не компилировать. Строка передаётся как `backend` в `torch.compile`,
например `inductor`. Компиляция удлиняет первую итерацию (иногда заметно) и
окупается на длинных прогонах.

## Что гарантирует шардирование

Ранги не делят данные через `DistributedSampler` — датасеты
(`TabularDataset`, `EventSequenceDataset`) шардируются сами, по записям, с
учётом и ранга, и воркера даталоадера. Из-за этого:

* **`DistributedSampler` использовать нельзя.** Он поделит уже поделённое.
* **При обучении все ранги должны получить одинаковое число батчей**, иначе
  один из них уйдёт в коллективную операцию, которую остальные не выполнят, и
  прогон зависнет до таймаута. За это отвечает `drop_tail: True` (по
  умолчанию): «хвост», не делящийся нацело между рангами, отбрасывается. На
  инференсе это требование снято — см. ниже.
* `rotate_tail: True` вместо отбрасывания сдвигает хвост от эпохи к эпохе, так
  что за несколько эпох модель всё-таки увидит все записи.

Валидация устроена иначе: если датасет шардируется, ранги считают метрики по
своим кускам и результаты собираются; если датасет реплицирован, каждый ранг
считает одно и то же, и метрики берутся с ранга 0.

### Инференс на нескольких картах: три режима

Валидация во время обучения всегда требует, чтобы ранги держали одинаковое
число батчей — за этим и стоит `drop_tail`. У инференса такого требования нет,
и `predict` выбирает один из трёх режимов:

| режим | когда | что происходит |
|---|---|---|
| `gather` | датасет шардирован и хотя бы одной метрике нужна вся популяция | пары `(батч, выход)` собираются на ранг 0, он считает метрики |
| `replicated` | датасет не шардирован | все ранги видят одни и те же записи, считает только ранг 0 |
| `local` | датасет шардирован и ни одной метрике популяция не нужна | каждый ранг кормит свои метрики своими строками и пишет свои файлы |

Решает флаг метрики `needs_full_population`. У `ScalarMetric` он `True`:
ROC-AUC, Qini и калибровка — не суммы, и посчитанные по кускам и усреднённые
дают другое число. У `ArtifactMetric` — `False`: продукт такой метрики это
строки в директории, а строкам всё равно, какой процесс их записал. Метрика,
которая ничего не объявила, считается нуждающейся в популяции — дорогой ответ
безопаснее.

Практически это значит, что типовой инференс — «посчитать скоры и сложить в
parquet» — **не делает ни одной коллективной операции**. Ранги не собирают
предсказания на ранг 0, а пишут параллельно, каждый свою часть. В имени файла
появился ранг (`..._rank-001_part-00000.parquet`) — без него два ранга внутри
одной секунды давали одинаковые имена и второй молча перезаписывал первого;
раньше это скрывал сам сбор на ранг 0. На одном процессе имена прежние.

### Хвост больше не обязан теряться

Раз в режимах `local` и `gather` цикл не требует равного числа батчей, инференс
может брать `drop_tail: false` — и тогда ни одна запись не остаётся без
предсказания:

```yaml
test_dataloader:
  dataset:
    _target_: avatar.data.TabularDataset
    drop_tail: false   # инференс сохраняет хвост
```

Так стоит во всех инференс-конфигах репозитория. В режиме `gather` ранг с
лишним батчем раньше уходил в `gather_object` в одиночку и прогон вис до
таймаута (по умолчанию 36000000 секунд — 417 суток); теперь ранги на каждом
шаге договариваются, остался ли у кого-нибудь батч, а добежавшие отправляют
пустую нагрузку. Проверено на корпусе из 101 записи и двух рангах: 50 и 51
запись, 1 и 2 батча, на выходе все 101.

Если `drop_tail` всё-таки оставлен включённым, `predict` теперь говорит об этом
вслух — с точным числом:

```
UserWarning: 1 of 101 records will not be scored: the dataset shards with
drop_tail=True, which drops the remainder that does not divide by world_size=2.
```

Для обучения `drop_tail: True` остаётся обязательным: там равное число шагов
нужно самому DDP, а не метрикам.

## Что происходит на каком ранге

Полезно при написании колбэков:

* Форвард, бэквард и шаг оптимизатора — на всех рангах.
* Хуки колбэков вызываются **на всех рангах**. Если действие должно случиться
  один раз (запись файла, лог в MLflow), проверяйте `ctx.env.is_main` сами.
* Метрики валидации целиком есть только на ранге 0.
* Поэтому решения, зависящие от метрик — «остановить обучение», «сохранить
  чекпоинт», — принимает ранг 0 и **рассылает** остальным
  (`DistEnv.broadcast_flag`), а не сводит по «хотя бы один». Иначе ранг, не
  видевший метрику, мог бы сохранить чекпоинт, который ранняя остановка
  запретила.

## Миграция с `accelerator:`

Старые конфиги описывали запуск одним блоком `accelerator:`. Он продолжает
читаться с `DeprecationWarning`; при наличии новых ключей побеждают новые.

| было в `accelerator:` | стало |
|---|---|
| `gradient_accumulation_steps` | `distributed.gradient_accumulation_steps` |
| `mixed_precision` | `amp` |
| `kwargs_handlers` → `DistributedDataParallelKwargs` | блок `ddp:` |
| `dynamo_plugin.backend` | `compile` |
| `dataloader_config` | удалено — соответствующее поведение обеспечивают сами датасеты |

Пример:

```yaml
# было
accelerator:
  gradient_accumulation_steps: 4
  mixed_precision: fp16
  kwargs_handlers:
    - _target_: accelerate.utils.DistributedDataParallelKwargs
      find_unused_parameters: True

# стало
distributed:
  gradient_accumulation_steps: 4
amp: fp16
ddp:
  find_unused_parameters: True
```

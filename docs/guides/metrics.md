# Метрики: контракт и точка расширения

Метрика — объект с тремя методами. Он накапливает состояние по батчам,
считает итог и обнуляется:

```python
class BaseMetric(abc.ABC):
    def update(self, inputs, outputs) -> None: ...
    def compute(self) -> dict[str, float]: ...
    def reset(self) -> None: ...
```

Цикл обучения вызывает их в этом порядке: `update` на каждом батче валидации,
затем один раз `compute`, затем `reset`. Возвращать что-либо из `update` не
нужно — все вычисления откладываются до `compute`.

Каталог готовых метрик — в [../reference/metrics.md](../reference/metrics.md).

## Что приходит в `update`

* `inputs` — батч, ровно в том виде, в каком его собрала collate-функция и
  получила модель. Это словарь: `targets`, идентификаторы, дополнительные
  колонки.
* `outputs` — то, что вернул пайплайн: датакласс из `fmlib.outputs` с
  `logits`, `loss` и полями конкретной задачи.

Отсюда следует практическое правило: **метрика привязана к паре
collate-функция + пайплайн**, а не к модели вообще. `UpliftMetrics` требует
`treatment_probs` и `control_probs`, которых у классификационного пайплайна
просто нет.

## Два вида метрик — и это разные базовые классы

Различие не в комментарии, а в типе, потому что от него зависит, что
возвращает `compute`.

**`ScalarMetric` — считает числа.** `compute` возвращает `{имя: значение}`, и
это попадает в лог и в раннюю остановку. Сюда относятся `UpliftMetrics`,
`ResponseMetrics`, `RegressionMetrics`, `MultiLossMetric`,
`UniversalLossesMetric` и обе обёртки.

**`ArtifactMetric` — пишет файл.** Наследник реализует `flush` — накопить,
записать, забыть, — а `compute` написан один раз в базовом классе: он вызывает
`flush` и возвращает **пустой словарь**. Сюда относятся `CollectEmbeddings`,
`InferenceMultiTaskCampaignMetrics`, `InferenceSupervisedMetrics`. Сборщики
сбрасывают накопленное на диск каждые `save_steps` батчей, поэтому переживают
прогон по десяткам миллионов записей.

Разделение появилось не из любви к иерархиям: пока базовый класс был один,
четыре сборщика возвращали из `compute` `None`, а цикл делает
`scores.update(metric.compute())`. Теперь `None` вернуть неоткуда.

Части файла именуются `<время старта>_part-00000[_префикс].parquet`. Номер
части монотонный: при сбросе каждые несколько батчей две записи в одну секунду
получали одинаковое имя, и вторая молча затирала первую.

## Как метрики считаются на нескольких рангах

Способ сведения выбирается по тому, шардируется ли датасет.

**Датасет шардируется** (обычный случай): каждый ранг проходит свой кусок, пары
`(batch, output)` собираются на ранг 0 через `gather_object`, и метрики считает
только он. Так сделано потому, что ROC AUC и подобные метрики неаддитивны: их
нельзя посчитать по частям и усреднить, нужна вся популяция в одном месте.

**Датасет реплицирован**: все ранги видят одни и те же записи. Сбор дал бы
каждую запись `world_size` раз, поэтому его нет. Форвард всё равно выполняют
все ранги — иначе один из них ушёл бы в коллективную операцию, до которой
остальные не дойдут, — но считает метрики только ранг 0.

В обоих случаях **`compute` вызывается только на ранге 0**, и полный набор
метрик есть только там. Именно поэтому решения, зависящие от метрик
(остановиться, сохранить чекпоинт), ранг 0 рассылает остальным, а не сводит
по «хотя бы один».

Сбор идёт через `gather_object` с `dst=0`, а не `all_gather_object`: полезная
нагрузка нужна одному рангу, и раздавать её всем — это `world_size`-кратный
трафик, который остальные тут же выбрасывают. `gather_object` не поддерживается
бэкендом NCCL, поэтому под пиклённые объекты заводится отдельная gloo-группа —
одна на прогон, создаётся при инициализации.

### Что именно уезжает по сети

По умолчанию — весь батч и весь выход модели: все входные тензоры, все скрытые
состояния, все головы. Метрика может сузить это, объявив, что читает:

```python
class MeanConfidence(ScalarMetric):
    required_inputs = ()
    required_outputs = ("logits",)
```

Тогда цикл соберёт union по всем метрикам списка и отправит только эти поля.
`None` — значение по умолчанию — означает «всё с этой стороны»: всегда верно и
всегда дорого. Стороны независимы, поэтому `UniversalLossesMetric`, которому
нужны все поля выхода, но ни одного ключа входа, всё равно позволяет выбросить
входные тензоры — обычно самые тяжёлые.

Выход при сужении **сохраняет свой класс и все поля**: незапрошенные
обнуляются, а не удаляются. Значит, проверять поле надо по значению
(`getattr(outputs, "x", None) is not None`), а не по наличию атрибута.

## Композиция

Метрики оборачиваются друг в друга. Две обёртки покрывают почти все нужды.

`GroupDevidedMetricsWrapper` **делит** популяцию: батч режется маской по
значениям заданных колонок, и каждый срез уходит в **свой** экземпляр метрики.
Экземпляры создаются лениво, когда встретилось новое сочетание, — поэтому
вложенная метрика задаётся фабрикой, а в конфиге это `_partial_: true`. Без
него все группы разделили бы один накопитель, и метрики молча стали бы
неверными.

`GroupAverageMetricWrapper` **усредняет** уже посчитанное. `update` он
пробрасывает как есть, а работает с именами, которые вернул вложенный
`compute`: `avg_over_regulars` усредняет по регулярному выражению над именами,
`groups` — по явному списку.

Регулярные выражения раскрываются заново на **каждом** `compute`: вложенная
обёртка открывает группы по мере их появления в данных, и группа, впервые
встретившаяся на второй эпохе, должна попасть в среднее. Если под выражение не
подошло ни одно имя, ключ не выдаётся вовсе и причина пишется в лог — раньше
такое среднее выдавалось нулём и читалось как обвал метрики.

Вместе они дают типовую конструкцию «посчитать по группам, потом усреднить»:

```yaml
metrics:
  valid_metrics:
    - _target_: fmlib.metrics.utils.GroupAverageMetricWrapper
      metric:
        _target_: fmlib.metrics.utils.GroupDevidedMetricsWrapper
        columns_to_devide: [target_attr_2, target_attr_3]
        columns_desc: [channel, group]
        metric_class:
          _target_: fmlib.metrics.ResponseMetrics
          _partial_: true
      avg_over_regulars:
        avg_control_roc_auc: ^channel_\d+_group_1_.*roc_auc_score
        avg_target_roc_auc: ^channel_\d+_group_0_.*roc_auc_score
```

Ловушка: группа, под которую не подошло ни одного имени, усредняется в **0**, а
не пропадает. Если регулярное выражение перестало совпадать после
переименования, вы увидите метрику, «упавшую в ноль», а не отсутствующую.

## Как написать свою метрику

```python
from fmlib.metrics import ScalarMetric


class MeanConfidence(ScalarMetric):
    """Средняя уверенность модели в предсказанном классе."""

    required_inputs = ()
    required_outputs = ("logits",)

    def __init__(self):
        self.total = 0.0
        self.count = 0

    def update(self, inputs, outputs) -> None:
        probs = outputs.logits.softmax(dim=-1).max(dim=-1).values
        self.total += float(probs.sum().detach().cpu())
        self.count += probs.numel()

    def compute(self) -> dict[str, float]:
        return {"mean_confidence": self.total / self.count if self.count else 0.0}

    def reset(self) -> None:
        self.total = 0.0
        self.count = 0
```

Подключается как обычный таргет:

```yaml
metrics:
  valid_metrics:
    _target_: mypackage.metrics.MeanConfidence
```

Что стоит соблюдать:

* **Наследуйтесь от `ScalarMetric` или `ArtifactMetric`**, а не от `BaseMetric`
  напрямую: они фиксируют, что возвращает `compute`.
* **`compute` возвращает словарь**, даже если значение одно и даже если
  значений нет — тогда `{}`. Цикл делает `scores.update(metric.compute())`, и
  скаляр или `None` вызовут ошибку.
* **`compute` не меняет состояние.** Два вызова подряд обязаны дать один и тот
  же ответ; очистка — дело `reset`, который цикл вызывает сам.
* **Значения должны быть скалярами**, приводимыми к `float`: в MLflow уезжают
  только числа.
* **Имена метрик — это API.** По ним настраивается ранняя остановка и по ним
  ищут обёртки-усреднители. Переименование метрики ломает конфиги молча.
* **Метрика не останавливает обучение.** Плохие данные — это предупреждение и
  пропущенный ключ, а не исключение из валидации: упавший `assert` внутри
  метрики убивает весь прогон. Если проверка важна, сделайте её числом и
  логируйте — так устроены `calibration_rank_shift_*` в `UpliftMetrics`.
* Снимайте тензоры с графа (`.detach()`) и уносите на CPU: метрика живёт
  дольше батча, и удержанный тензор удержит и весь граф.

## Несколько метрик сразу

`valid_metrics` может быть списком — тогда считаются все, а результаты
объединяются в один словарь:

```yaml
metrics:
  valid_metrics:
    - _target_: fmlib.metrics.ResponseMetrics
    - _target_: fmlib.metrics.MultiLossMetric
```

Имена при этом не должны пересекаться: словари сливаются, и последний
победит.

# Цикл обучения

Обучение выполняет `avatar.train.Trainer`. Всё, что не является форвардом,
бэквардом, шагом оптимизатора, границей накопления, AMP, `no_sync` у DDP, шагом
планировщика и переносом батча на устройство, вынесено в колбэки — см.
[callbacks.md](callbacks.md).

Ключи конфига, управляющие этим, перечислены в
[../configuration/schema.md](../configuration/schema.md).

## Что происходит за эпоху

```
для каждого батча:
    перенос на устройство
    on_batch_begin
    [no_sync, если это не граница накопления]
        forward  ──► on_forward_end
        backward ──► on_backward_end
    если граница накопления:
        обрезка градиента, шаг оптимизатора, шаг планировщика
        on_optimizer_step, on_step_end
        [валидация, если задан steps_before_evaluation]
после эпохи:
    on_epoch_end
    [валидация, если steps_before_evaluation не задан]
```

Два счётчика, которые легко перепутать: `micro_step` растёт на каждом батче, а
`global_step` — только на границах накопления. Планировщик, ранняя остановка и
`steps_before_evaluation` считают в `global_step`.

## Когда происходит валидация

Ровно одно из двух:

* `steps_before_evaluation: null` (по умолчанию) — раз в эпоху, после
  `on_epoch_end`;
* `steps_before_evaluation: N` — каждые N шагов оптимизатора, внутри эпохи.

Если `valid_dataloader` не задан, валидации не происходит вообще, и ранняя
остановка с чекпоинтами по метрике не работают.

## Сохранение по умолчанию, вето от колбэка

Порядок внутри валидации важен и устроен так:

1. считаются метрики;
2. цикл выставляет `control.should_save = True` — **сохранять по умолчанию**;
3. срабатывает `on_evaluate`, и колбэк ранней остановки **снимает** флаг, если
   метрика не улучшилась;
4. ранг 0 рассылает итоговые решения остальным;
5. если флаг выжил, срабатывает `on_save`.

Отсюда единственное ограничение на порядок колбэков: колбэк ранней остановки
должен идти **до** колбэка чекпоинтов. Иначе чекпоинт запишется раньше, чем его
успеют запретить.

Рассылка (а не сведение «хотя бы один») тоже не случайна: метрики есть только на
ранге 0, поэтому остальные ранги не могут иметь мнения. Сведение по «хотя бы
один» позволило бы рангу, не видевшему метрику, сохранить чекпоинт, который
ранняя остановка запретила.

## Чекпоинты

Каталог — `best_models/{experiment_name}/{run_name}/{global_step}/`, в нём два
файла:

| файл | что внутри | кто читает |
|---|---|---|
| `checkpoint.pt` | веса, оптимизатор, планировщик, `GradScaler`, счётчики, состояние ГПСЧ | возобновление обучения |
| `model.bin` | только веса | инференс и финальный тестовый прогон |

`max_saved_checkpoints: N` оставляет N последних по времени записи каталогов.

Если `run_name` не равен `debug`, а каталог уже существует, запуск падает на
старте — защита от затирания чужого прогона.

## Возобновление

Два разных сценария:

```yaml
train:
  model_state: best_models/exp/run/42/model.bin   # только веса
```

Загружает веса и обучает с нуля по счётчикам. Это дообучение с новой задачей
или новым расписанием.

```yaml
train:
  checkpoint_state: best_models/exp/run/42/checkpoint.pt
  start_epoch: 7
```

Восстанавливает состояние оптимизатора, планировщика, масштабировщика потерь,
номер шага и состояние генераторов случайных чисел. Это продолжение
прерванного прогона; `start_epoch` задаётся отдельно.

## Финальный тестовый прогон

Если задан `test_dataloader`, после обучения цикл сам находит каталог с
**наибольшим** номером шага, грузит из него `model.bin` и считает
`test_metrics`. Метрики уезжают с префиксом `test_`.

Поиск идёт по числовому значению имени каталога, а не по алфавиту — иначе шаг
«8» оказался бы новее шага «16».

## Смешанная точность и обрезка градиента

`amp: fp16` включает `autocast` в float16 и масштабирование потерь; `bf16` —
только `autocast`, масштабирование bf16 не нужно. Масштабировщик активен только
на CUDA.

Если задан `clip_grad_norm`, масштабирование снимается **до** обрезки: обрезать
масштабированный градиент значило бы обрезать по неверной норме.

## Накопление градиента

При `gradient_accumulation_steps: N` синхронизация градиентов между рангами
пропускается на всех микрошагах, кроме последнего (`no_sync`) — ради этого
накопление и нужно. Потери делятся на N перед `backward`.

Два следствия: эффективный размер батча равен `batch_size * world_size * N`, а
планировщик шагает раз на границу накопления, поэтому бюджет шагов —
`эпохи * батчи / N`.

## Что цикл ожидает от даталоадера

**Датасет шардируется сам.** `DistributedSampler` использовать нельзя — он
поделит уже поделённое.

**Все ранги должны получить одинаковое число батчей.** Иначе один ранг уйдёт в
коллективную операцию, до которой остальные не дойдут, и прогон повиснет до
таймаута (по умолчанию он очень большой). За это отвечает `drop_tail: True`.

Если у датасета есть метод `set_epoch`, цикл вызывает его в начале каждой
эпохи — так работает `rotate_tail`.

## Использование `Trainer` напрямую

Из Python цикл собирается без Hydra:

```python
from avatar.train import Trainer, DistEnv, RunConfig
from avatar.training_arguments import TrainingArguments

trainer = Trainer(
    model=model,
    optimizer=optimizer,
    scheduler=scheduler,
    train_dataloader=train_loader,
    valid_dataloader=valid_loader,
    valid_metrics=metrics,
    training_arguments=TrainingArguments(num_epochs=3),
    run_config=RunConfig(),
    env=DistEnv.from_env(),
    callbacks=[...],
    checkpoint_dir="checkpoints",
)
scores = trainer.train()
```

Все аргументы именованные. `env` и `run_config` можно не передавать — они будут
построены по умолчанию, что даёт однопроцессный запуск в fp32.

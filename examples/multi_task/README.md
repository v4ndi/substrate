# Multi-task: MMoE и PLE

Запускаемый пример обучения нескольких задач над общим пулом экспертов.
Данные генерирует скрипт, выгружать ничего не нужно.

Устройство пайплайнов — в
[../../docs/guides/models.md](../../docs/guides/models.md), каталог классов — в
[../../docs/reference/pipeline.md](../../docs/reference/pipeline.md).

## Запуск

```bash
python examples/multi_task/generate_data.py
```

Скрипт печатает готовые команды. Обе версии обучаются за пару минут на CPU:

```bash
python -m avatar.train --config-dir=examples/multi_task/configs \
    --config-name=mmoe data_dir=/абсолютный/путь/examples/multi_task/data

python -m avatar.train --config-dir=examples/multi_task/configs \
    --config-name=ple  data_dir=/абсолютный/путь/examples/multi_task/data
```

За три эпохи `valid_roc_auc_score` доходит до ~0.99 у обоих. На этих данных
разница между MMoE и PLE не принципиальна — задача синтетическая; пример
показывает, **как их собрать**, а не какой из них лучше.

## Что в данных

Три задачи над одним и тем же признаковым пространством, с намеренно разными
целевыми функциями: задачи 0 и 1 делят большую часть сигнала, задача 2 почти
независима. Смесь экспертов имеет смысл ровно тогда, когда задачи расходятся в
том, какие признаки важны.

| колонка | что это |
|---|---|
| `cat_features`, `num_features` | признаки, как после препроцессинга |
| `task_name` | к какой задаче относится запись (`"0"`, `"1"`, `"2"`) |
| `group_id` | группа кампании |
| `target` | бинарный таргет |

## Три вещи, которые легко собрать неправильно

**Пайплайну нужен `group`.** `MMoE.forward` принимает `group` как обязательный
позиционный аргумент, а collate его сам не добавляет. Отсюда:

```yaml
collate_fn:
  _target_: avatar.data.MultiTaskSupervisedCollateFn
  add_extra_columns: {group: group_id}
```

**Ключи `heads` должны быть строками-числами.** Внутри пайплайн делает
`int(task_name)` и сопоставляет с идентификатором из `task_mapping`. Поэтому в
YAML это `"0"`, `"1"`, `"2"` в кавычках — иначе получится не тот тип ключа.

**Задача, от которой в батче меньше двух записей, пропускается.** Её потери на
этом шаге равны нулю. Отсюда `drop_last: True` и не слишком маленький
`batch_size`: при батче 512 и трёх задачах на каждую приходится ~170 записей.
При батче 32 задачи начнут регулярно выпадать, и обучение станет рваным.

## Про `num_features` в агрегации

```yaml
aggregation_config:
  name: linear
  num_features: 25    # 8 категориальных + 16 числовых + 1 токен группы
  emb_dim: 32
```

`n_groups: 2` включает эмбеддинг группы, который по умолчанию **добавляется
отдельным токеном** (`ConcatTreatmentInteraction`). Забыть про эту единицу —
самая частая ошибка размерностей в multi-task конфигах.

## `find_unused_parameters: True`

В блоке `ddp:` он здесь не для красоты: голова задачи, которой не досталось
записей в батче, не получает градиента, и DDP на это ругается. Для
однопроцессного запуска настройка ничего не меняет.

## Чем отличаются MMoE и PLE

`configs/ple.yaml` наследуется от `configs/mmoe.yaml` через `defaults:` и переопределяет ровно
два блока — `model._target_` и `tabular_encoder`. Это и есть вся разница между
архитектурами.

| | MMoE | PLE (CGC) |
|---|---|---|
| пул экспертов | общий целиком | общие + приватные под каждую задачу |
| что видит гейт задачи | всех экспертов | `[общие] + [свои]` |
| число модулей-экспертов | `num_experts` | `num_shared + num_tasks * num_specific` |

Приватные эксперты считаются **на задачу**: `num_specific_experts: 1` при трёх
задачах — это три модуля, а не один.

Смысл PLE в изоляции: гейт одной задачи не может утянуть весь пул за собой.

## Как посмотреть на гейты

Веса гейтов выкладываются в выход как `task_gated_weights`, и их читают две
диагностические метрики:

```yaml
metrics:
  valid_metrics:
    - _target_: avatar.metrics.RocAucScore
    - _target_: avatar.metrics.Entropy
    - _target_: avatar.metrics.Importance
```

`Entropy` близко к 1 означает, что задача распределена по экспертам; близко к 0
— что она схлопнулась на одного. `Importance` отвечает на тот же вопрос с
другой стороны: 0 — нагрузка равномерна.

## Балансировка потерь

В примере — простейший вариант, фиксированные веса:

```yaml
multi_task_loss:
  _target_: avatar.losses.multi_task.MultiTaskLoss
  loss_balancer:
    _target_: avatar.losses.multi_task.WeightLossBalancer
    loss_weights: {"0": 1.0, "1": 1.0, "2": 1.0}
```

Альтернативы, когда задачи на разных масштабах:
`UncertainlyLossBalancer` (учит веса как гомоскедастичную неопределённость),
`GradNormLossBalancer` (выравнивает нормы градиентов), `PCGradBalancer`
(проецирует конфликтующие градиенты). Все описаны в
[../../docs/guides/losses.md](../../docs/guides/losses.md).

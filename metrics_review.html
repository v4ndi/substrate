Ревью модуля avatar.metrics

Схема сведения метрик по рангам в новом трейне выбрана правильно. Но между контрактом, докстрингами и кодом накопился разрыв, который некому было поймать: на 3024 строки модуля приходится один тестовый файл.

Ревизия 598799e · refactor/data-sharding-hdfs Объём 3024 строки · 25 классов · 13 файлов Дата 10.09.2026
3 дефекта роняют прогон B1 – B3
12 тихо портят числа S1 – S12
6 устойчивость и стоимость P1 – P6
50% модуля не используется 12 из 25 классов

1. Резюме

Модуль устроен правильно по крупному счёту: контракт update / compute / reset описан в документации, отделены считающие числа метрики от сборщиков файлов и от бенчмарков, композиция через обёртки работает. Новый цикл avatar/train/evaluate.py решил самую тяжёлую задачу верно: неаддитивные метрики (ROC AUC, qini) считаются по всей популяции на ранге 0, а не по шардам с усреднением.

Проблема в другом. Ниже 3 дефекта, ломающих прогон, и 12, тихо портящих числа. Половина воспроизводится в три строки — и это, собственно, диагноз: без тестов расхождения между тем, что написано в докстринге, и тем, что считает код, копились молча.

Всё, помеченное запущено, воспроизведено на этой ревизии скриптом metrics_review_repro.py, а не выведено чтением. Помеченное по коду — вывод из чтения.

2. Что сделано хорошо

Отмечаю, чтобы при правках это не потерялось.

Режим сведения выбирается по признаку шардирования датасета

Реплицированный датасет не собирается — иначе каждая запись попала бы в метрику world_size раз. Форвард при этом выполняют все ранги, чтобы никто не завис на коллективе. Тонкое место, сделано верно.

compute только на ранге 0, и решения рассылаются оттуда же

Альтернатива — сводить «хотя бы один ранг сказал стоп» — привела бы к рассинхрону чекпоинтов между рангами.

Обёртка групп требует _partial_: true, и это объяснено

Без фабрики все группы делили бы один накопитель. Ровно та ошибка, которую легко сделать и невозможно заметить по логам.

UniversalLossesMetric находит поля рефлексией

Новая вспомогательная функция потерь начинает логироваться без правки конфига.

Документация модуля выше среднего по репозиторию

Описан и контракт, и оба режима сведения, и композиция обёрток. Именно поэтому расхождения кода с ней так хорошо видны.

3. Дефекты, ломающие прогон

B1

Четыре сборщика возвращают None из compute() — новый трейн падает на этом

запущено

Цикл делает scores.update(metric.compute()) в трёх местах: валидация, инференс и train-метрики. А compute() не возвращает ничего у четырёх классов:

КлассГдеСсылок в конфигах
InferenceMultiTaskCampaignMetricscampaign.py:44523
ClassificationInferenceMetricsbase.py:1874
InferenceMultiTaskResponseMetricscampaign.py:5520
InferenceSupervisedMetricssupervised.py:5410
 
{}.update(None)  ->  TypeError: 'NoneType' object is not iterable

Это регрессия рефакторинга: в базовой ревизии 7c96504 инференс делал scores = metrics.compute() и спокойно жил с None. Новый predict() превратил это в падение — в самом конце прогона, уже после того, как parquet записан. Данные не теряются, но задача завершается с ненулевым кодом.

Соседний CollectEmbeddings.compute возвращает {} и работает: правильный ответ в модуле уже есть, просто не везде.

Фиксreturn {} в четырёх местах — минута работы. Но настоящая причина в контракте, см. предложение 1.
B2

assert внутри метрики убивает обучение

на практике

Это ровно то, обо что споткнулась кампания сравнения обучений в прошлой задаче.

assert abs(calib_c_roc_auc - c_roc_auc) < 0.01
assert abs(calib_t_roc_auc - t_roc_auc) < 0.01

Проверка сама по себе разумная: бета-калибровка монотонна и не должна менять ранжирование. Но недообученная модель выдаёт почти константные скоры, ROC AUC на них шумит сильнее 0.01 — и валидация роняет весь прогон обучения. Метрика не должна иметь права остановить обучение: её задача — сообщить число.

ФиксПревратить проверку в метрику: писать calibration_rank_shift в результат и предупреждать при превышении порога. Проблема видна в MLflow, прогон живёт.
B3

RegressionMetrics схлопывает все метрики в один ключ

запущено

supervised.py:433:

f"{task_name}_" if len(task_name) != 0 else "" + key: val

Приоритет операторов разбирает это как (f"{task_name}_") if cond else ("" + key). При непустом task_name ключом становится "prod_a_" — без имени метрики. Все три метрики пишутся в один ключ, выживает последняя: 

{'mse': 1.0, 'mae': 2.0, 'mape': 3.0}  ->  {'prod_a_': 3.0}

При пустом task_name ветка другая и всё корректно, поэтому дефект виден только в многозадачном режиме.

ФиксКак в соседних классах: f"task_{task_name}_{key}" if len(str(task_name)) != 0 else key.

4. Дефекты, тихо портящие числа

S1

Entropy возвращает энтропию с обратным знаком

запущено

moe_reg.py:35 считает sum(p·log p) / log(n), тогда как нормированная энтропия — это −sum(p·log p) / log(n): 

равномерно по 4 экспертам -> -1.0000   докстринг обещает ~ +1
коллапс на одного         -> -0.0000   докстринг обещает ~  0

Метрика монотонна и как индикатор работает, но знак и интервал не те, что написаны: дашборд с «энтропией −1 = здорово» читается наоборот. Соседний ExpertsWorkload берёт минус правильно — в модуле две реализации одной величины с разным знаком.

S2

MultiLossMetric: среднее отношений вместо отношения сумм, и compute не идемпотентен

запущено

Три дефекта в двадцати строках:

  1. Считается mean(loss_i / n_i) вместо sum(loss_i) / sum(n_i). На батчах (2, 4) и (4, 2) получается 1.25 вместо корректной 1.0 — ровно то смещение, которое докстринг обещает устранить.
  2. compute() мутирует self.losses, подменяя список числом. Второй вызов даёт 0.46875 — мусор. Контракт явно требует «Should not modify internal state».
  3. if self.num_items[attribute] != 0 сравнивает список с нулём — всегда истина, ветка else недостижима.
S3

UniversalLossesMetric делит на глобальный счётчик батчей

запущено

Докстринг обещает: потеря, применимая не ко всем батчам, усредняется по тем, где она есть. Код использует общий update_counter. Потеря, присутствующая в 1 батче из 4 и всегда равная 1.0, логируется как 0.25. Плюс среднее по батчам не взвешено размером батча — последний неполный батч имеет тот же вес, что и полный.

S4

RocAucScore возвращает nan, и один nan навсегда выключает раннюю остановку

запущено

Защита асимметрична: sum(targets) > 0 ловит срез без единого позитива (возвращается 0.5), но не ловит срез из одних позитивов — там sklearn предупреждает и возвращает nan. Дальше: 

elif score < self.best_score + self.delta:   # nan < nan  ->  False

Сравнение с nan всегда ложно, поэтому исполняется ветка «улучшение»: best_score = nan, счётчик обнуляется. После этого любой следующий скор тоже даёт False — ранняя остановка не сработает уже никогда, а best_metric останется nan.

ФиксПроверять len(set(targets)) > 1, а не сумму; и научить EarlyStopping пропускать нечисловой скор вместо того, чтобы принимать его за рекорд.
S5

GroupAverageMetricWrapper фиксирует regex-группы на первом compute

запущено

Список имён под регулярное выражение вычисляется один раз. А обёртка, делящая популяцию, создаёт группы лениво, по мере появления в данных: 

эпоха 1 -> {'g_0_auc': 1.0, 'avg_auc': 1.0}
эпоха 2 -> {'g_0_auc': 1.0, 'g_1_auc': 0.0, 'avg_auc': 1.0}

Среднее по определению не полное, и в логах это не видно. Обёртка используется в 21 конфиге — самая популярная в модуле.

ФиксПересчитывать группы на каждом compute — это дешёвый поиск по десяткам имён, кэшировать нечего.
S6

UpliftMetrics: калибратор обучается и проверяется на одних и тех же строках

по коду

Если в батче нет колонки split_type — а её нет во всех конфигах пилота, — весь срез помечается как "calib". Тогда тестовая маска пуста, калибратор фитится на калибровочном срезе и на нём же оценивается, и в главную метрику прогона уходит in-sample число. Проверка is_calib=True при этом всегда проходит именно потому, что данные те же — она проверяет не качество, а тождество.

ФиксБез split_type либо не выдавать калиброванные метрики вовсе, либо считать их cross-fitting'ом. Второе честно и стоит одного лишнего прохода по массиву.
S7

require_calibration: False не отключает калибровку

на практике

Флаг влияет только на то, какая метрика попадает в mean_*. Калибраторы фитятся всегда, ассерты из B2 выполняются всегда. Пользователь, выключивший флаг, чтобы обойти падение, обнаружит, что оно осталось. Имя параметра обещает не то, что он делает.

S8

При require_calibration: True две разные метрики получают одно значение

по коду

mean_calibrated_X и mean_X записываются из одного и того же списка. Некалиброванное среднее в этом режиме получить невозможно, хотя ключ для него в логе есть.

S9

Метрика молча дописывает в данные позитивный пример

по коду 
if y_true.sum() == 0:
    y_true[0] += 1

Мотив понятен и честно описан в докстринге. Но происходит это без единой строчки в логе, а += 1 вместо = 1 на неудачных данных даст метку 2. Правильнее вернуть nan или пропустить группу — и сказать об этом.

S10

PLEResponseMetrics: ключ перезаписывается в цикле

по коду

В глобальной ветке _any_specific_expert_mean пишется внутри цикла по индексу эксперта, а значение от этого индекса зависит. Все итерации, кроме последней, выброшены; итоговое число — сумма по хвосту от последнего индекса, а не «утилизация специфичных экспертов». Класс мёртв, но если его будут оживлять — это первое, что нужно поправить.

S11

SequenceStats делит на размер первого батча

по коду

Знаменатель — len(context_lengths) * self._batch_size, где _batch_size запомнен с первого батча. Последний батч почти всегда неполный, значит средняя длина контекста систематически занижена.

S12

Обёртка групп не забывает группы при reset()

по коду

Сбрасываются вложенные метрики, но не словарь групп. Группа, бывшая на первой эпохе и исчезнувшая на второй, останется, и её пустая метрика попадёт в compute. Контракт требует «as if newly instantiated».

5. Устойчивость и стоимость на новом трейне

Здесь ничего не сломано, но новый трейн изменил цену этих решений.

P1

all_gather_object там, где нужен gather_object(dst=0)

по коду

dist.py:132 собирает объект на все ранги, после чего результат отбрасывается везде, кроме нулевого. Трафик и пиковая память завышены в world_size раз без всякой пользы.

P2

Через сеть гоняются целые батчи, включая то, что метрике не нужно

по коду

Сериализуется (batch, output) целиком: все входные тензоры, все скрытые состояния, все головы. RocAucScore читает из этого два поля. При record-level шардировании это и есть главный потолок пропускной способности валидации.

Отдельно: TrainMetricsCallback делает этот сбор на каждом шаге обучения, а не раз в эпоху.

Дешёвый фиксДать метрике декларацию нужных полей — required_inputs / required_outputs — и собирать только их.
P3

os.makedirs(..., exist_ok=False) роняет второй запуск

по коду

Директория от предыдущего прогона приводит к FileExistsError при создании метрики — то есть до начала обучения. Соседние места в том же модуле используют exist_ok=True. Разнобой.

P4

Имена файлов с точностью до секунды затирают друг друга

по коду

Пять мест строят имя из datetime.now() с точностью до секунды. Сборщики сбрасывают буфер каждые save_steps батчей; два сброса внутри одной секунды — обычное дело, и второй parquet молча затирает первый. Нужен монотонный счётчик части.

P5

Обёртка групп не работает на train-метриках

запущено

copy.deepcopy(outputs) безопасен на валидации (inference_mode), но на выходе обучающего шага тензоры не листовые: 

RuntimeError: Only Tensors created explicitly by the user
(graph leaves) support the deepcopy protocol at the moment.

Плюс сам по себе deepcopy всего выхода на каждую группу и каждый батч — это лишние копии порядка «групп × размер батча», тогда как нужен только срез логитов.

P6

print вместо логгера в семи местах

по коду

В многоранговом прогоне это перемешанный вывод без отметки ранга. Один из семи (sequence_stats.py:69) печатает весь словарь статистик на каждый compute — отладочный вывод, забытый в коде.

6. Что предлагаю поменять

1. Разделить контракт на «числа» и «файлы»

Сейчас compute() обязан возвращать dict[str, float], но половина наследников по смыслу возвращает файл. Отсюда четыре класса, забывшие return {}, и падение на самом ходовом конфиге. 

class ScalarMetric(BaseMetric):
    def compute(self) -> dict[str, float]: ...

class ArtifactMetric(BaseMetric):
    def flush(self) -> None: ...          # пишет parquet
    def compute(self) -> dict[str, float]:
        self.flush()
        return {}                          # один раз, в базовом классе

Цикл тогда не может получить None в принципе — не потому, что все наследники аккуратны, а потому, что возвращать None неоткуда. Дешевле, чем ловить это ревью.

2. Перейти на контракт torchmetrics для аддитивной части

Индустриальный стандарт для PyTorch — torchmetrics.Metric: состояние объявляется через add_state(..., dist_reduce_fx=...), синхронизация между рангами происходит внутри compute(). Что это даёт здесь:

  • аддитивные метрики сводятся all_reduce по нескольким скалярам вместо пересылки батчей — это снимает P2 для большей части метрик;
  • неаддитивные (BinaryAUROC есть готовый) гоняют по сети только preds и target, а не весь батч с эмбеддингами;
  • исчезает целый класс дефектов S2 / S3 — накопители пишутся декларативно.

Специфичные для задачи метрики — uplift, qini, кампанейские сборщики — на torchmetrics не переводятся и остаются своими. Их и стоит оставить: в них ценность модуля. Реалистичный порядок: сначала предложения 1 и 3, потом RocAucScore → BinaryAUROC как пилот.

3. Декларация нужных полей вместо пересылки всего батча

Самое выгодное соотношение «эффект / объём правки» из всего списка: две строки на метрику плюс фильтр в цикле оценки и в train-колбэке.

4. Метрика не имеет права останавливать обучение

Убрать assert из uplift.py (B2) и из sequence_stats.py:105 — там assert hasattr(...) is not None, выражение всегда истинно, проверка декоративная. Общее правило: невалидные данные → предупреждение и пропуск ключа; исключение допустимо только при конструировании метрики, до старта обучения.

5. Числовая гигиена на границе

  • Возвращать float(...), а не np.float64 и не внутренний defaultdict — две метрики отдают наружу собственное состояние, и вызывающий может его испортить.
  • Не писать nan в результат: пропускать ключ и предупреждать. Тогда S4 не сможет сломать раннюю остановку, даже если проскочит.
  • EarlyStopping должен явно игнорировать нечисловой скор.

6. Убрать тройное дублирование блока task/group

UpliftMetrics.compute, ResponseMetrics.compute и RegressionMetrics.compute — три копии одного ~100-строчного цикла с одинаковым хвостом сохранения submit'а. B3 живёт ровно в той копии, куда исправление не доехало. Общий _TaskGroupScorer убирает ~200 строк и один класс дефектов.

7. Опечатки в публичном API

GroupDevidedMetricsWrapper, параметр columns_to_devide, файл group_devided_wrap.py (правильно — divided). Переименовать с шимом на один релиз — тем же приёмом, каким только что убрали шимы в avatar/nn. Класс используется только в двух yaml внутри docs/, так что цена сейчас минимальна; через полгода будет выше.

8. Тесты

Главный пункт: без него остальные не удержатся. Минимум:

  • контрактные тесты, параметризованные по всем классам модуля: compute() дважды подряд даёт одно и то же; reset() возвращает в исходное состояние; compute() всегда возвращает dict. Эти три теста ловят B1, S2 и S12 разом;
  • золотые значения против sklearn / sklift на фиксированном массиве — ловит S1, S2, S3, S11;
  • краевые случаи: срез из одних позитивов, из одних негативов, пустой, группа появляется на второй эпохе — ловит S4 и S5.

7. Анализ мёртвого кода

Правило. Символ достижим, если его имя встречается где-либо в репозитории вне собственного файла: в коде, в Hydra-конфиге, в тесте, в документации. Правило заведомо переоценивает достижимость, поэтому ноль ссылок — сильное свидетельство, а ненулевое число не доказывает ничего.

Два уточнения, чтобы таблицу не читали слишком буквально:

  • BaseInferenceMetric машина помечает мёртвым, но это ложное срабатывание: правило не смотрит внутрь самого пакета, а его наследник ClassificationInferenceMetrics живой. Класс нужен.
  • SequenceStats не мёртв и не жив: у него есть единственный на весь модуль тест, но нет ни одного конфига.

Отдельно про два класса из таблицы:

  • ExpertsWorkload нельзя использовать, даже если захотеть: его compute возвращает скаляр, а не словарь, и scores.update(...) на нём упадёт. Это честно написано в его собственном докстринге — класс документирован как неработающий и оставлен в __all__.
  • GroupDevidedMetricsWrapper — единственный, кого жалко: он описан в руководстве как одна из двух основных обёрток, а его пара живёт в 21 конфиге. Но в рабочих конфигах он не встречается ни разу. Это не «удалить», это расхождение документации с практикой: либо обёртку начать использовать, либо переписать раздел документации.

Что предлагаю удалить: MMoEResponseMetrics, PLEResponseMetrics, InferenceSupervisedMetrics, InferenceCampaignMetrics, InferenceMultiTaskResponseMetrics, ExpertsWorkload, HiddensNorm — семь классов, 654 строки, без единой ссылки за пределами документации; два из них вдобавок содержат известные дефекты. Остальные четыре — обсудить: возможно, они нужны внешним конфигам вне репозитория, как были нужны шимы avatar.nn.

8. Порядок работ

Оценки — по объёму правки, не по календарю.

Сначала — правит поведение, полчаса на всё

  1. B1 — return {} в четырёх compute. Разблокирует 23 конфига кампании.
  2. B3 — приоритет операторов в supervised.py:433.
  3. S4 — проверка на два класса вместо суммы, плюс EarlyStopping, игнорирующий nan.
  4. B2 — assert → предупреждение и метрика calibration_rank_shift.

Потом — правит числа

  1. S2, S3 — накопители в MultiLossMetric и UniversalLossesMetric.
  2. S1 — знак энтропии, и убрать вторую реализацию.
  3. S5 — пересчёт regex-групп на каждом compute.
  4. S6, S7, S8 — честная калибровка и осмысленный require_calibration.

Параллельно — без этого предыдущее развалится обратно

  1. Контрактные тесты по всем классам модуля, золотые значения, краевые случаи.

Затем — структура

  1. Удалить мёртвое.
  2. Разделить ScalarMetric / ArtifactMetric.
  3. required_inputs / required_outputs и фильтрация перед сбором; gather_object(dst=0) вместо all_gather_object.
  4. Общий _TaskGroupScorer вместо трёх копий.
  5. Переименования с шимом; RocAucScore → BinaryAUROC как пилот на torchmetrics.
